# 喵喵旅账产品需求文档（PRD）

版本：0.1 Approved
日期：2026-09-21
产品形态：微信小程序
目标版本：MVP
状态：APPROVED

## 1. 产品定义

喵喵旅账是一款面向结伴旅行人群的共享记账与结算小程序。同行成员在旅行中共同维护一本账，系统持续计算每个人的垫付、应承担金额和净额，并在旅行结束时生成清晰、可执行的转账方案。

一句话价值主张：**旅行中随手记，结束时不用算。**

## 2. 背景与用户问题

多人旅行的费用记录通常分散在个人备忘录、支付记录和微信群里。旅行结束后，组织者需要重新收集并核对账单，再人工计算谁应该向谁转账。

核心问题包括：

1. 账目分散，容易漏记、重复记或找不到付款记录。
2. 每笔消费的参与人不同，简单均分不能覆盖真实场景。
3. 成员不知道自己垫付、应付和应收多少，容易产生误解。
4. 结算需要由一个人集中计算、解释并催款，既耗时又有社交压力。

当前替代方案是微信群、备忘录、Excel 或旅行结束后当面计算。这些方式可以完成任务，但缺少同一账本、即时同步、权限控制和自动结算。

## 3. 产品目标与非目标

### 3.1 MVP 目标

- 让多人在同一行程中查看和记录费用。
- 让一笔常见费用在 30 秒内完成记录，最多 5 个主要操作步骤。
- 在记账成功后即时刷新，并在重新进入页面时同步每名成员的垫付、应承担和净额。
- 行程结束时生成可解释的转账清单，减少人工计算和转账次数。
- 支持创建者邀请微信成员，也支持添加无需微信登录的离线成员。

### 3.2 MVP 非目标

- 不直接发起微信支付或自动转账。
- 不支持人民币以外的货币和汇率换算。
- 不做发票识别、支付账单自动导入或 AI 分类。
- 不做复杂财务报表、Excel 导出或朋友圈长图。
- 不保证在完全离线状态下多人实时协作；仅保留本地草稿并在恢复网络后提交。
- 不提供严格数学意义上的“全局最少转账次数”承诺，只提供减少转账次数、结果可复核的结算方案。

## 4. 目标用户

| 用户角色 | 描述 | 核心诉求 |
| --- | --- | --- |
| 行程创建者 | 发起旅行并负责组织，通常垫付较多 | 快速建群、掌握全局、完成结算 |
| 普通成员 | 同行朋友，会付款或参与分摊 | 少操作、账目透明、知道自己应付或应收多少 |
| 离线成员 | 未加入小程序，由其他成员代记 | 能参与分摊，不阻塞全团记账 |

首个典型场景：4 人结伴去云南 7 天，A 垫付住宿，B 垫付租车，餐饮由不同成员轮流付款。成员旅途中共同记账，结束当晚查看系统生成的转账方案。

## 5. 关键产品原则

1. **先记下来，再补细节**：金额与付款人优先，备注、地点等信息不得阻塞提交。
2. **默认值覆盖大多数情况**：默认付款人为自己，默认全员参与，默认均分。
3. **结果必须可解释**：每个人都能从结算结果返回相关账单，理解金额来源。
4. **修改必须可追踪**：关键账目变更保留操作者、时间和变更摘要。
5. **不替用户移动资金**：MVP 只计算与确认，不代表实际付款已经发生。

## 6. MVP 用户流程

### 6.1 创建并邀请成员

1. 用户进入首页，点击“创建行程”。
2. 填写行程名称，可选填目的地和日期。
3. 创建成功后进入行程详情页。
4. 创建者生成带高熵 `inviteId` 的原生小程序分享路径。
5. 微信用户授权基础资料后加入；创建者也可手动添加离线成员。

### 6.2 快速记一笔

1. 点击底部常驻“记一笔”。
2. 输入金额。
3. 确认付款人，默认当前用户。
4. 选择参与人，默认全部成员。
5. 选择均分或按份额分摊并提交。

分类默认“其他”，用户可在提交前选择餐饮、交通、住宿、门票、购物或其他。备注为可选项；消费时间是必填存储字段，默认当前时间，用户可修改但不可留空。

### 6.3 查看个人状态

在行程详情页，每名成员都能看到：

- 全团累计消费。
- 自己累计垫付。
- 自己应承担金额。
- 自己当前净额：应收或应付。
- 最近账单和修改记录。

### 6.4 生成结算方案

1. 任意活跃成员可查看基于当前账本临时计算的结算预览；预览不持久化，也不会通知其他成员。
2. 创建者点击“发起结算”，系统基于当前 `ledgerRevision` 创建不可变结算快照和转账清单。
3. 发起结算不会锁死账本；后续新增、编辑或删除账单会使当前快照失效，并将行程标记为“需重新结算”。
4. 创建者手动生成新版本；旧版本保留为只读记录。
5. 付款方将转账项标记为“已支付”，收款方确认后标记为“已收款”。付款方只能在收款确认前撤销“已支付”。
6. 全部转账项均为“已收款”后，行程状态变为“已结算”。

账本变更保护：若当前活跃结算尚无任何 `paid` 或 `received` 转账，账单变更可以使其失效；一旦出现已支付或已收款项，系统禁止修改账本。若尚无 `received`，创建者可先将争议项全部重置为 `pending` 再修改；若已有 `received`，必须先完成本轮结算。完成后只能通过新增“调整账单”修正差异，已纳入完成结算的历史账单不可编辑或删除。调整账单递增 `ledgerRevision`、将 Trip 改为 `needs_settlement`，但不改变历史 Settlement 的 `completed` 状态。

## 7. 功能需求

### 7.1 首页与行程管理

- 展示“进行中”“待结算”“已结算”三个分组；`active` 归入进行中，`needs_settlement` 和 `settling` 归入待结算，`settled` 归入已结算。
- 支持创建、编辑、归档行程。
- 一个用户可以参与多个行程。
- 创建字段：名称必填；目的地、开始日期、结束日期选填。
- 行程状态：`active`、`needs_settlement`、`settling`、`settled`、`archived`。
- 创建者可以移除尚未关联账单的成员；已有账单的成员只能停用，不能直接删除。
- 已归档行程只读；恢复为进行中后才允许继续记账。
- MVP 固定上限：行程名称 30 字、成员 20 人、单行程有效账单 5,000 笔。
- 创建者身份只能转让给同一行程中的活跃微信成员，不能转让给离线成员。转让必须在同一云函数事务中更新 `Trip.ownerUserId`、原创建者和新创建者的 `Member.role`，并写入审计记录。

### 7.2 成员与邀请

- 微信成员通过原生小程序分享路径加入，路径只携带不可预测的 `inviteId`，不直接携带权限或成员身份。
- 加入前展示行程名称、创建者和成员数量。
- 用户确认后才加入行程。
- 支持离线成员，仅由创建者添加、改名或停用；活跃成员可在记账时选择离线成员参与分摊。
- 同一微信用户在同一行程中只能对应一个成员。
- 成员显示名可以在行程内单独设置，不修改微信昵称。
- 邀请默认 7 天失效、最多成功加入 20 次；创建者可以提前撤销并重新生成。
- 邀请只在云函数中校验有效期、使用次数、行程状态和成员上限；重复加入直接返回已有成员身份。

权限矩阵：

| 操作 | 创建者 | 活跃普通成员 | 停用成员 |
| --- | --- | --- | --- |
| 查看行程与历史账单 | 是 | 是 | 是，只读 |
| 新建账单 | 是 | 是 | 否 |
| 编辑/删除自己创建的账单 | 是 | 是 | 否 |
| 编辑/删除他人账单 | 是 | 否 | 否 |
| 添加、改名、停用离线成员 | 是 | 否 | 否 |
| 生成邀请、发起结算、归档行程 | 是 | 否 | 否 |
| 转让创建者身份 | 是 | 否 | 否 |

### 7.3 账单

账单字段：

- 金额，人民币，精确到分，必须大于 0 且不超过 ¥999,999.99。
- 付款人，单选，默认当前成员。
- 参与人，多选，至少 1 人。
- 分摊方式：均分、按份额。
- 分类：餐饮、交通、住宿、门票、购物、其他。
- 备注，可选，最多 100 字。
- 消费时间，必填，默认当前时间，可修改但不可留空。
- 创建者、创建时间、最后修改者、最后修改时间。

分摊规则：

- **均分**：金额按参与人数平均；无法整除的分值按照 `Member.createdAt`、`Member.id` 升序分配，确保分摊总额严格等于账单金额。
- **按份额**：每名参与者填写 1 至 999 的整数份额；个人承担额按份额比例计算，尾差使用同一稳定顺序处理。
- 付款人可以不在参与人中，用于“替别人付款”场景。
- 默认参与人仅包含当前 `active` 成员；历史账单保留创建时的参与成员，不因成员停用而改变。

权限规则：

- 账单创建者和行程创建者可以编辑或删除账单。
- 其他成员只能查看。
- 服务端必须校验权限，不能只依赖客户端按钮隐藏。
- 编辑和删除产生审计记录；删除采用软删除，结算计算忽略已删除账单。
- 每条账单包含递增 `revision`。编辑或删除请求必须携带 `expectedRevision`；版本不一致时云函数返回最新账单，客户端只能选择重新编辑或取消，禁止静默覆盖。
- 账单详情向全体行程成员展示简要审计事件，按 `createdAt` 倒序分页；软删除账单仅保留在审计记录中，不出现在普通账单列表。
- 新建账单必须携带客户端生成并持久化的 `clientRequestId`。云函数以 `(tripId, createdByUserId, clientRequestId)` 去重；网络超时后的重试返回已创建账单，不得重复入账。

### 7.4 近实时统计

对每名成员计算：

- `paidAmount`：有效账单中该成员作为付款人的金额总和。
- `owedAmount`：有效账单中该成员分摊金额总和。
- `netAmount = paidAmount - owedAmount`。
- `netAmount > 0` 表示应收，`netAmount < 0` 表示应付。

所有成员净额之和必须为 0 分。若不为 0，系统禁止发起结算并记录异常。

“近实时”在 MVP 中指：写入成功后当前设备立即重新拉取统计；页面 `onShow` 和用户下拉刷新时重新同步。首版不承诺后台常驻推送或离线多人自动合并。

### 7.5 结算

- 结算以“分”为整数单位计算，禁止使用浮点数。
- 将债务人和债权人按绝对净额排序，逐步匹配并生成转账项。
- 每个转账项包含付款人、收款人、金额和状态。
- 结算方案必须满足：每名成员完成方案后的余额为 0，所有转账金额均大于 0。
- 方案目标是减少转账次数和理解成本，不承诺任意输入下的数学全局最优。
- MVP 不发送订阅消息；行程页面展示待确认和待支付状态。
- 结算快照保存 `ledgerRevision`、成员净额、账单版本摘要和转账项，生成后不可修改。
- 任一被允许的有效账单写入都会在同一事务中递增 `Trip.ledgerRevision`。若存在尚未发生付款的活跃结算，则将其标记为失效并清空 `activeSettlementId`；已完成的历史结算保持 `completed` 和只读。系统不自动创建新方案，由创建者手动确认后生成新版本。
- 转账状态机为 `pending → paid → received`；付款方可执行 `pending → paid` 和确认前的 `paid → pending`，收款方可执行 `paid → received`。创建者只能将争议项重置为 `pending`，操作必须写入审计记录。
- 只有 `Trip.activeSettlementId` 指向、且状态为 `active` 的结算转账可以改变状态。失效、完成或被新版本替代的结算及其转账全部只读，不得再次影响行程状态。
- 生成结算时，云函数先读取账本 revision `R` 并分页计算；写入前必须在事务中再次断言 `Trip.ledgerRevision === R`，再创建 Settlement、SettlementTransfer，并更新 `activeSettlementId` 和 `latestSettlementId`。同一 `(tripId, ledgerRevision)` 最多存在一个 active Settlement；重复请求返回已存在的方案。若 revision 断言失败，返回“账本已变化”，客户端刷新后重试，禁止保存混合版本快照。
- 收款确认必须在单一云函数事务中完成：确认该方案仍为 active、更新目标转账为 `received`、检查全部转账状态；若均已收款，则同时将 Settlement 标记为 `completed`、Trip 标记为 `settled` 并清空 `activeSettlementId`。并发确认必须得到同一最终状态。

### 7.6 本地草稿与同步

- 新建账单页面自动保存未提交草稿。
- 网络不可用时允许继续编辑草稿，但不显示“已同步”。
- 恢复网络后由用户主动提交。
- MVP 不自动合并多人离线修改，避免静默覆盖数据。

## 8. 页面信息架构

1. **首页**：行程列表、创建行程入口。
2. **创建/编辑行程页**：基本信息、成员管理。
3. **行程详情页**：总消费、我的净额、成员概览、账单列表、记一笔、发起结算。
4. **新增/编辑账单页**：金额、付款人、参与人、分摊方式、分类、备注。
5. **账单详情页**：账单内容、每人承担额、变更记录、编辑/删除入口。
6. **结算页**：成员净额、转账方案、支付/收款状态。

## 10. 技术与架构方案

### 方案 A：本地单机原型

数据全部存放在微信本地缓存。开发快，但无法实现多人共享同一本账，不满足核心产品目标。

### 方案 B：微信云开发 MVP（推荐）

小程序前端配合云数据库、云函数和微信身份。共享、权限和部署路径与微信生态一致，适合快速上线验证。

### 方案 C：独立后端服务

使用独立 API、数据库和对象存储。长期控制力更强，也便于跨平台，但第一版的认证、部署和运维成本更高。

**选择方案 B。** 第一版需要真实多人协作，而不是只能演示的本地账本；微信云开发能够以较低复杂度覆盖身份、共享数据和服务端权限校验。

## 11. 非功能需求

| 项目 | 要求 |
| --- | --- |
| 性能 | 在正常 4G/Wi-Fi 真机环境下，常用读操作 p95 小于 1 秒；10 人、500 笔账单的结算云函数 p95 小于 2 秒，包含冷启动的结果单独记录 |
| 金额正确性 | 所有金额使用整数分；任一账单分摊合计必须等于账单金额 |
| 兼容性 | 最低微信基础库 2.20；开发和发布前在主流 iOS、Android 设备验证 |
| 隐私 | 账单仅行程成员可访问；不强制获取手机号；日志不记录完整账单内容 |
| 安全 | 云函数校验身份、行程成员关系和角色权限；客户端不可直接越权修改数据 |
| 可恢复性 | 写入失败时明确提示并保留表单内容，不允许无提示丢账 |
| 可观测性 | 记录云函数错误率、账单创建失败、结算校验失败和邀请加入失败 |

## 12. 异常与边界情况

- 金额为 0、负数、超过 ¥999,999.99 或小数超过两位时禁止提交。
- 参与人为空时禁止提交。
- 行程只剩一名成员时允许记账，但不生成转账项。
- 成员退出或停用后，历史账单和结算关系保留。
- 两人同时编辑同一账单时，后提交者因 `expectedRevision` 冲突收到最新内容，只能重新编辑或取消，不静默覆盖。
- 发起结算后发生账单变更，旧方案标记为过期；创建者确认后手动生成新版本。
- 当前活跃结算已有 `paid` 或 `received` 转账时禁止改账；完成结算后以新增调整账单修正，历史账单和历史结算保持只读。
- 创建者本人退出前必须转让创建者身份。
- 邀请链接失效、行程归档或用户已加入时，页面给出明确状态。
- 删除账单后必须重新校验所有成员净额之和为 0。

## 13. MVP 验收标准

### 行程

- 创建者可以创建行程并生成邀请入口。
- 第二个微信用户可以加入同一行程，并在两个设备上看到一致的成员和账单数据。
- 创建者可以添加离线成员。
- 已撤销、已过期或达到使用上限的邀请无法加入行程。

### 记账

- 用户可以创建均分账单和按份额账单。
- 账单金额与所有成员分摊金额之和完全一致。
- 创建者可以编辑任意账单；普通成员不能编辑他人账单。
- 写入失败时表单数据不会丢失。
- 使用旧 revision 编辑账单会收到冲突提示，已有数据不会被覆盖。

### 统计与结算

- 每名成员的垫付、承担和净额计算正确。
- 所有成员净额之和始终为 0 分。
- 系统生成的转账方案可以让所有成员余额归零。
- 标记完成所有转账后，行程状态变为已结算。
- 已结算后补记账单会使原结算方案过期，创建者可以手动生成新版本。
- 付款方不能代替收款方确认“已收款”，创建者重置争议项会产生审计记录。

### 端到端验收场景

使用 4 名成员和至少 8 笔费用覆盖：全员均分、部分成员参与、付款人不参与、按份额分摊、尾差分配、并发编辑冲突、编辑账单、删除账单、生成结算、双向确认和结算后补记。两个真实微信账号分别操作并核对结果。

## 14. 发布与指标

### MVP 指标

- 账单创建完成率。
- 账单创建耗时中位数。
- 创建行程后成功邀请至少一人的比例。
- 有效行程中生成结算方案的比例。
- 结算方案中至少一笔转账被确认的比例。
- 次周再次创建或参与新行程的用户比例。

`结算率 ≥ 60%`、`周留存 ≥ 30%` 作为验证目标，不作为首版上线门槛；需先定义有效行程并积累真实样本。

### 发布阶段

1. 开发者工具单人功能验证。
2. 两个微信账号的多人联调。
3. 4 至 10 人真实旅行灰度测试。
4. 根据账单创建失败、漏记和结算争议反馈修正。
5. 提交微信体验版与正式审核。
